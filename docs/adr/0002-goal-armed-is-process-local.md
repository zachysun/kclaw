# ADR-0002：goal 循环的 armed 是进程内开关（重启不自动续跑）

状态：已接受（2026-09-27）

## 背景

`/goal` 目标循环（见 [goal](../core/goal.md)）需要一个"循环是否在自续"的开关。目标快照本身持久化在 `meta.goal`（事件流投影），开关放哪里有两种选择：跟着快照持久化（重启后自动恢复续跑），或只放进程内（重启后目标在、循环停，等用户显式 resume）。

## 决策

**armed 只放进程内**（`GoalLoopHost` 的 `GoalRuntime.armed`），不持久化到事件流或 meta。daemon 重启后：目标快照、轮数、token 计数、判定历史全部还在（事件派生，不受重启影响），但循环不自动续跑；用户 `/goal resume`（或 WebUI 面板恢复）才重新 armed 起跑。

进程内同生灭的还有三个字段：`judging`（检查互斥）、`windDownPending`（收尾轮标记——armed 都没了收尾无从谈起）、`lastEnqueuedMessageId`（撤销排队轮的句柄，队列本身随重启清空）。

## 理由

1. 目标循环的语义是"授权这台 daemon 自主连续花钱"：每轮都是真实的 run + 判定器调用。重启清掉了用户的会话内上下文（确认 broker、进行中的 run），一个刚醒来的 daemon 不该默认继续烧钱。
2. 反方向（自动续）的正当场景不存在：用户重启 daemon 的意图要么是维护、要么是换配置，都不是"请继续跑目标"；真想继续的用户 resume 一次即可，计数与 budget 都还在。
3. 实现上事件流保持纯审计：armed 若持久化，"重启后是否续跑"就成了事件流里一个可写状态，派生逻辑要多一种非事件来源的权威数据，收益只有省用户一次 resume。

## 后果

- 停机语义简单：`dispose()` 只需等进行中的检查落定，无"重启恢复"路径要测。
- 代价是诚实告知：WebUI 面板与 `/goal` 状态显示 armed 状态，重启后用户看得到"目标在、循环停"。
- 换这一决策需要把 armed 写进 `goal.set` 事件并处理与快照状态的合并，目前无此计划。
