# ADR-0003：目标裁决放在 run 边界，由 daemon 侧独立判定器执行

状态：已接受（2026-09-27）

## 背景

`/goal` 目标循环要回答"目标达成了吗"。两种自然做法：

1. **模型自报**：给干活模型一个 `goal_report` 工具，让它自己宣称完成；
2. **独立判定**：每轮 run 结束后，daemon 在 run 边界另起一次无工具的 LLM 调用，拿目标 + 验收输出 + 对话证据做裁决。

调研的 8 家 harness 里两种都有：自报的（若干 coding agent 的 "task complete" 惯例）实现最省，但完成判定与完成动机落在同一个上下文里——模型说服自己比说服裁判容易得多。

## 决策

**裁决不放给干活模型**：不给它任何 goal 相关工具、不问它"完成了吗"。判定发生在 **run 边界**（RunManager 的空闲边缘 `onSessionIdle`）：独立的判定器调用（温度 0、无工具、严格 JSON 三值裁决 not_met/met/impossible），证据只有目标原文、本轮验收命令输出、对话尾部窗口。验收门在判定器之前执行且失败短路——命令没过就不花判定 token，失败输出直接作为下一轮的修正指引。

判定器模型独立可配（`config.goals.judge` 命中 provider 条目，未配置回退会话模型线），与干活模型可以不是同一个。

## 理由

1. **利益分离**：干活模型有"宣称完成以停止干活"的动机梯度，裁判与选手必须不是同一次调用。证据规则（只看验收输出与对话事实、不听自述）写进判定器 system 提示词。
2. **run 边界是天然的判定点**：run 内判定意味着打断工具循环或依赖模型主动求助，run 边界判定让循环驱动完全在 daemon 侧（机械上限、熔断、收尾轮都不需要模型配合）。
3. **三值裁决而非二值**：`impossible`（需求自相矛盾、前提缺失、外部依赖永久失效）单独一值，把"硬撑十轮"变成提前终态；提示词要求慎用，拿不准判 not_met。
4. 验收门先行是防骗的最硬一环：命令在沙箱里真实执行，判定器看到的是 exit code 与输出尾部，不是转述。

## 后果

- 每轮多一次 LLM 调用（判定器用量单独记录、计入目标 token budget）；换来的是完成判定的错误率与干活模型的措辞解耦。
- 判定器自身的失败模式要独立治理：解析/传输两类连败分别熔断（3 次/5 次），未熔断时 fail-open 续跑并明确告知模型"本轮无外部裁决、自行验收"。
- 判定器可能判错（证据窗口看不到远处事实）：连判无进展 3 轮会停摆而不是死循环，用户 resume 即可推翻。
