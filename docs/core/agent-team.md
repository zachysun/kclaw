# agent-team — agent 团队（组长 + 组员协作）

## 职责

一个主会话可以调 `create_team` 把自己变成**组长**，再用 `spawn_teammate` 添加若干**组员**：每个组员是一个持久的子会话，有自己的系统提示词、自己的收信箱和自己的 run。协作以**任务板**为中心：组长拆任务，组员认领任务、汇报进展，人随时可以对任一成员说话。实现分两半：`packages/core/src/team/`（存储 `TeamStore` 与提示词）与 `packages/server/src/team.ts`（团队宿主：身份反查、收信箱投递、自动派活、面板）。

## 设计决策

- **协作以任务为中心，不以对话为中心**：组员之间不互相对话（收信箱只允许 组长→组员 / 组员→组长），一切协同落在任务板的状态上（认领、依赖、结题）。这是刻意的设计——自由群聊会让多 agent 的上下文互相污染，任务板的 CAS（compare-and-swap，写入前核对版本号、不一致就拒绝）才是可靠的协作面。
- **组员是持久子会话**：`parentSessionId` 指向组长，因此复用子会话的一切基建（列表默认隐藏、用量归组、记忆提取排除），但不继承 subagent 的两条限制——组员的 run 不随父会话停止而停止（见下），也不在派发后销毁。
- **收信箱是持久化的投递队列**：消息先写进收信人的收信箱文件（`<workspace>/.kclaw/teams/<队名>/inboxes/<名字>.json`），再渲染成目标的一次 run。`pending`（未投递）→ `delivered`（已投）的翻转发生在**输入真正落进目标会话历史之后**（监听该 run 的第一条 `message.created`）——崩溃窗口里最坏是重投一次，永远不会丢（at-least-once，至少一次投递）。
- **运行模型没有级联停止**：唤醒只来自三个来源——组员收信箱有信、用户指名说话、自动派活。除此之外组员空闲待命，不存在"组长停了组员跟着停"；停止永远是逐个的（用户在成员卡上停某一个，或 CLI 对该成员会话发 `run.cancel`）。唯一的例外是删除/清除组长会话：那是数据生命周期（级联删子会话），顺手取消还在跑的组员 run。
- **审计数据在目录，事件流只作记录**：任务、名单、收信箱的数据都保存在 `.kclaw/` 团队目录的 JSON 文件里；`team/*` 七种审计事件追加在**组长的**事件流上供审计页回放，每条带 `version` 字段（当前为 1，由宿主统一注入），写入是尽力而为（失败降为一条警告，团队操作本身照常），不进 meta 投影、不推进 `updatedAt`。

## 团队目录（数据所在）

```
<workspace>/.kclaw/teams/<队名>/
  config.json              # 团队记录 + 组员名单：teamId（即队名）、名字、leadSessionId、members
  inboxes/team-lead.json   # 组长的收信箱
  inboxes/<名字>.json      # 每个组员一个收信箱：{"version":1,"entries":[...]} 单个 JSON 文件
<workspace>/.kclaw/tasks/<队名>/
  task-<id>.json           # TaskSnapshot 全量快照：主题/详情/状态/认领人/依赖/attempt/revision
  current_tasks/<id>-<slug>.txt   # 进行中任务的锁文件（任务 id、主题、认领人、attemptId、认领时间）
```

`teamId` **就是队名**（目录名的锚点），在工作区内唯一；同一队名删除归档后可复用，任务 id 用「现存最大值 + 1」派生、永不复用。队名来自建队时的显式起名；默认从会话标题取（标题不是合法队名时回退到 `team`），撞了已存在的队名就顺延 `-2`、`-3` 去重；名字会成为目录名，只收字母数字（任何文字都行，中文可以）加连字符，最长 32 字符，显式起名撞了已存在的队会明确报错。建队时把 `.kclaw/` 尽力追加进工作区 `.gitignore`（已有条目则不动）。

**current_tasks 锁**是"这条任务正在被执行"的可见投影：任务进入 in_progress 时写锁文件，到达终态或改主题时移除；宿主加载团队目录时做一次对账（`reconcileLocks`）——清掉任务文件已经不认的残留锁，为还在进行中的任务补写锁，崩溃遗留的锁就是一次执行被中断的痕迹。

**身份反查**：团队宿主 `find()` 扫描 `.kclaw/teams/`（跳过 dot 开头的归档目录）。`config.json.leadSessionId` 命中即组长、`members` 里的子会话 id 命中即对应组员。run 组装在每次 run 前调用一次 `facade.describeSession(sessionId)`，拿到的身份决定这个 run 的一切团队特化。查询结果为 null 时分两种：不在团队里的 subagent 会话与 job 会话拿不到任何团队工具；**主线会话拿到一个"预备组长"身份**：七个工具都在表面上（身份是 lead），`create_team` 由此可达，其余团队动作会被 facade 以明确的冲突报错拒绝（队还不存在）。崩溃遗留的 provisioning（添加中途断电）在组长下次被检测时按磁盘上的实际状态定为 active / failed。

## 身份与提示词

- **组长**：主提示词后追加一段组长协议（拆任务按文件边界切、指派或放给自动派活、验收结题信、常驻无级联停止）。追加发生在 `assembleSystemPrompt` 的基座文本上，而基座文本按 run 逐次与冻结基线比对——所以建队后的**第一个 run** 就热生效，不用等缓存纪元。
- **组员**：整套换成组员提示词（人设、任务板工具用法、按序处理收信箱、结题要给组长发 `send_message`）。组员**没有** `create_team` / `spawn_teammate`（不能建队、不能添加——团队不递归），权限处理与主会话相同。
- 首次 run 的输入前缀一段 `<system-reminder kind="team-identity">`，把"你是谁、在哪个队"一次讲清。

`run.started` 的 `trigger` 枚举因此多了 `"team"`：团队投递的 run 以它记录来源。该触发值不参与技能调用包装、不触发自动命名、消息无条件入流，并且绕过子会话的 user 提交拒收（投递的是组长/队友的信，不是用户插话）。

## 七个团队工具（`tools/team.ts`）

| 名称 | 谁有 | 职责 |
|------|------|------|
| `create_team` | 主线会话 | 建队并使本会话成为组长（一个会话只属一个队；组员没有） |
| `spawn_teammate` | 仅组长 | 添加组员：建持久子会话、固化模型快照、初始任务走收信箱 |
| `send_message` | 全体 | 给组长或队友写信；组员的默认目标就是组长 |
| `list_agents` | 全体 | 列出组员名单（名字、状态、在忙、当前任务） |
| `task_create` | 全体 | 在任务板上建任务（可带依赖；**直接指派他人是组长专属**） |
| `task_update` | 全体 | 按 revision 改任务；认领未认领任务时自动填自己的名字 |
| `task_list` | 全体 | 列任务板全貌 |

表面按身份收缩：不在团队里的会话（job 会话、非组员的 subagent 会话）一个都没有；组员拿上面 5 个；组员同时是子会话（`childRun`），再按 subagent 规则裁掉 `memory_save` 与 `subagent_run`（单层结构，组员不能再派 subagent，提示词里同样写明）。任务认领与状态变更必须回传 `expected_revision`（服务端 CAS 比对）；认领同时铸造 `attemptId`，被取代的执行者拿着旧 id 的迟到写入会被拒绝，不会覆盖继任者的结果。

## 收信箱与投递

一封信的投递过程：`enqueueMail` 写文件（持久）→ 渲染：该目标收信箱里所有**未在途**的 pending 条目拼成一次 run 的输入 → `submit(trigger: "team", disposition: "steer")` → 监听到输入落地（目标会话的第一条 `message.created`）才翻转 delivered。**目标在忙时不投递**：信留在收信箱，等它当前 run 结束的空闲边再送——同一局面内已渲染进在途 run 的条目有在途记录去重，不会投两次。

**并发上限 `team.maxActive`**（默认 4）：同时运行的组员数到顶后，新信留在收信箱；任一组员的 run 结束（空闲边）都会触发 `pumpIdle` 排空积压。组长的唤醒不占组员额度。

**自动派活**：空闲边顺带扫描任务板——就绪（依赖全部完成）且未认领的任务派给一个空闲、无未读信、未持有任务的组员，提示它用 `task_update` 认领后推进。一份 **offer 记录**（局面纪元 + 任务 id）防止死循环：同一局面对同一任务只唤醒一次；任何入信、建任务、改任务都会推进纪元、重新开放派发。**冷恢复**走同一条路：空闲边发现组员持有进行中任务却闲置（比如 daemon 重启后），按记录「一局面一次」的规矩唤醒它继续推进。

## 停止与删除

- 组员在跑时，WebUI 成员卡显示「停止」——对**组员自己的会话**发 `run.cancel`，组长照常不受影响。
- 组长被停止不会波及组员（没有父停子停）。
- `DELETE /sessions/:id`（软删）与 `POST /sessions/:id/purge` 在级联删子会话的同时，先取消该队还在跑的组员 run（`cancelMembersForLead`），再把团队目录与任务目录整体移进各自的归档位：`teams/<队名>` 移到 `teams/.archive/<队名>`，`tasks/<队名>` 同理（重名追加时间戳后缀，记录与轨迹仍可查）。这是数据生命周期的一部分，不是运行模型的级联停止。
- **一人一任务**：存储层在认领与改派两处强制「一个组员同时最多一条进行中任务」，第二次认领或把进行中任务改派给持有别的任务的人都会被明确拒绝。

## 用户面

- **`GET /sessions/:id/team`**：团队面板数据（团队、身份、组员名单、任务板）。组员与组长都能取；不在任何团队 404。
- **WS `send_message` 的 `target` 字段**：带 target 的发送定向投递给该组员（经收信箱）；消息同时落进**组长的历史**并附一条「已转发给组员 X」的 note，组长的上下文知道用户对谁说了什么。WebUI 对这条发送不做乐观回显（落地的 `message.created` 会广播回来）。反向的**组员来信**（`send_message` 写给组长）同样作为原文整条 user 消息落进组长历史，WebUI 在对话流里把它们渲染成 agent 一侧的折叠条（多条合并计数、展开才见正文）。组长的上下文保有全文，对话页不刷屏。
- **WebUI 对话页团队面板**：建队后出现在消息流顶部——成员卡（生命周期徽标、忙闲、当前任务、逐个停止、审计跳转）+ 任务板（状态统计、依赖、认领人、尝试次数）。点组员卡「说话」把输入框目标切成「→ 组员名」（粘性，点组长卡或 × 切回）。
- **确认卡 / 提问卡转发**：组员 run 里的人工确认与提问转发到组长频道，标注「来自组员 X」；在组长频道裁决，效果回到组员。

## 配置

| 键 | 默认 | 说明 |
|----|------|------|
| `team.maxMembers` | `8` | 名单上限（含失败的添加） |
| `team.maxActive` | `4` | 同时运行的组员上限；满员时新信排队等空闲边 |
| `team.mailbox.maxUnreadPerTarget` | `64` | 单个收信箱未读上限，超限投递方收到明确报错 |
| `team.mailbox.maxMessageBytes` | `65536` | 单条信的字节上限 |
| `team.taskBoard.maxTasks` | `64` | 任务板总量上限（含终态任务），超限建任务报错 |
