# compaction — 上下文压缩

## 职责

会话聊得越长，每次发给模型的上下文就越大，大到超出模型窗口后请求会直接失败。压缩机制把较早的对话转换成摘要、之后不再按原文发送，让每轮发送量回到预算以内；被压掉的细节仍然留在硬盘上，并可通过 `session_search` 检索回来。整套机制分四层，互相独立：

1. **触发与分界**（`packages/core/src/session/compaction.ts` 的 `estimateContextTokens` / `chooseBoundary`）：按 token 估算判断何时压缩、压到哪里。触发点有五个——后台预压、收尾压缩、中途压缩、超限紧急急救、手动 `/compact`——都不在"用户发送消息"的路径上，发送永不等待压缩。
2. **分层摘要**（同一模块的 `renderSegment` 加压缩引擎的编排——core `packages/core/src/session/compactor.ts` 的 `Compactor.compact`）：两次不带工具的模型调用，先给新压掉的段生成"段摘要"，再归并进"总摘要"。
3. **工具输出省略**（`packages/core/src/agent/context.ts` 的 `toProviderMessages`）：每次构造请求时在省略预算内从最新往回保留工具结果，装不下的换成一行占位文字，防止一次运行内的多次工具调用把上下文撑爆。
4. **后台预压缩**（压缩引擎的 `Compactor.background`）：占用进入预压区间就派一次后台压缩——前台继续运行不等它，摘要在后台生成、写入元数据后暂存，等下一次迭代边界再应用，把"等压缩"的等待从关键路径上挪走。

外围还有三件配套物：`session_search` 工具（检索函数 `packages/core/src/tools/session-search.ts`，直接扫会话事件流）负责"找得回来"；手动压缩（`RunManager.compactSession` + HTTP/CLI/web 三个入口）负责"人能主动压"；压缩审计（事件流里的 `compaction` 事件）负责"压过之后查得到"。调模型与写入磁盘的编排在 core 的压缩引擎 `Compactor`（见上文第 2 层）完成，`RunManager` 只保留手动压缩入口。

## 设计决策

- **按 token 触发，不按消息条数**：一条消息可能是 10 个字也可能是一次返回 100KB 的工具输出，条数说明不了上下文大小。触发判断用估算：基准取最近一次真实请求的大小（最后一条助手消息记录的 `usage.inputTokens`，模型供应商返回的真实数字，天然含系统提示与工具定义的固定开销），基准之后的新消息按字符粗算（`estimateTokens`：CJK 字符每个记 0.75 个 token，其余字符四个记 1 个，结果向上取整）。估算整体偏大而非偏小——偏大只会让压缩提前发生，方向安全。
- **细节只损失一次**：更早的做法是每次压缩都把旧摘要重新压一遍，细节一轮轮丢失。现在的机制把摘要拆成两层——**段摘要**针对一段对话生成之后永不修改，**总摘要**只做"旧总摘要 + 新段摘要"的归并。细节只在新段摘要素成时损失一次，总摘要随时可以从全部段摘要重跑归并重新生成（段摘要是不变的底稿，不依赖对话原文）。
- **保留部分对齐用户消息**：分界起点固定落在一条用户消息上，保证压掉的段和保留的部分都是从"用户提问"开始的完整轮次，工具调用和它的结果永远在同一侧——OpenAI 兼容接口要求两者配对出现，拆开会直接报错。
- **压缩不挡发送，失败不挡运行**：五个触发点全部不在发送路径上——发送消息后立即开始运行，压缩要么发生在运行结束后的收尾、要么在运行中途的迭代边界（中途与后台预压）、要么是对超限错误的急救重试。摘要调用抛错时发出 `result:"failed"` 的结束事件并记日志，运行照常继续，下一次过线重新触发；压缩事件（含投影）追加失败只记日志，不发失败事件（见"边界与出错"）。最坏情况等于"没有压缩"，不会比现状差。
- **同一会话至多一个压缩在跑**：后台预压与同步压缩（中途/收尾/急救/手动）共用一张"正在执行"登记表，同步路径遇到正在执行的后台压缩时等它结束、重新估算占用后再决定，而不是并发两个摘要调用互相踩写。等来的后台成果不浪费：直接应用，或作为同步压缩的保底（等完发现占用已降回线以下，就用后台成果、不再压一次）。
- **检索与审计是外围，不是前提**：`session_search` 每次调用都重新读一遍事件流，没有需要维护或重建的持久索引；审计是事件流里的一条 `compaction` 事件，追加失败只记日志，不让已成功的压缩回退。
- **循环窗口退居保险**：agent 循环"最多取最近 N 条消息"的硬上限从 40 放宽到 200（`packages/core/src/agent/loop.ts`），角色从主要控制手段退化为防止估算彻底失准的极端保险。

## 术语

| 术语 | 含义 |
|------|------|
| 压缩 | 把较早的对话消息转换成摘要、之后不再按原文发送的过程。原文始终保留在硬盘上。 |
| 压缩段（段） | 一次压缩中被转换成摘要的那段连续消息。 |
| 段摘要 | 针对一个压缩段生成的摘要，固定五个栏目（见下文），生成之后永不修改。 |
| 总摘要 | 所有段摘要归并成的一份完整脉络，每轮发给模型的就是它。 |
| 脉络项 | 总摘要进入模型请求的形态：一条 user 消息——交接声明 + `<compacted-summary>` 标签包裹的总摘要——垫在请求 messages 的最前面（见"注入"）。 |
| 分界 | 压缩内容和保留原文部分的边界，用一条消息的 id 表示。 |
| 保留部分 | 分界之后、继续按原文发送的近期历史。 |
| 预算 | 一个会话允许的上下文 token 上限：取 `sessions.contextTokens`（默认 128000）与模型条目 `providers.entries.<key>.contextWindow` 中的较小者；两者都没配时 128000。所有预算读数（各道触发线、压缩引擎、打包预算）经 `resolveContextTokens` 统一解析，模型窗口一收紧则全线收紧。 |
| 占用估算 | 对"当前会话全部未压缩历史"的 token 估算值（`estimateContextTokens`），是各道触发线的读数来源。 |
| 省略线 | 预算的 70%（`compactPackRatio`）：请求组装时工具输出省略的预算值。 |
| 预压线 | 预算的 75%（`compactAheadRatio`）：后台压缩的触发下限（上限是红线）。 |
| 黄线 | 预算的 80%（`compactAtRatio`）：收尾压缩的触发线。 |
| 红线 | 预算的 90%（`compactPanicRatio`）：中途压缩的触发线，也是后台压缩的触发上限。 |
| 后台压缩 | 预压区间内启动的非阻塞压缩：前台继续运行，摘要在后台生成，完成后写入元数据、暂存待应用（见"机制四"）。 |
| 工具输出省略 | 构造请求时在预算内从最新往回保留工具结果原文，装不下的换成一行占位文字；只影响发出的请求，不影响存储。 |

## 数据模型

压缩状态有两处体现（目录结构见 [storage](./storage.md)）：`meta.json` 的 `compaction` 字段（由 `compaction` 事件投影）与事件流里 append-only 的 `compaction` 事件（压缩审计本身）。压缩事件对投影还有第二个效果：**清除 `meta.systemBaseline`**（冻结的系统提示词基线）——压缩改写消息历史，provider 前缀缓存必然全量失效，正是系统提示词重新装配、重新固化基线的边界（见 [hooks](./hooks.md) 的冻结基线一节）。

### meta.json 的 `compaction` 字段

`SessionMeta`（`packages/core/src/session/store.ts`）上的可选字段，类型定义在 `packages/core/src/session/compaction.ts`；它由 `compaction` 事件**投影**而来（`applyEvent` 每次把新段折进 `segments`、更新 `top`/`upto`），`updateMeta` 不再直接合并它：

```ts
export interface CompactionSegment { upto: string; summary: string }
export interface CompactionState { segments: CompactionSegment[]; top: string; upto: string }
```

| 字段 | 含义 |
|------|------|
| `segments[].upto` | 这个压缩段覆盖到的最后一条消息 id（含它） |
| `segments[].summary` | 这个段的段摘要 |
| `top` | 总摘要 |
| `upto` | 总分界：这条消息之前（含它）都已压缩，之后的是保留部分（等于末段的 `upto`） |

段的消息范围由相邻两个 `upto` 界定：第一段从会话开头（或旧格式升级点）到 `segments[0].upto`，其后每段从前一段的 `upto` 之后到本段 `upto`（`segmentRanges` 负责映射）。分界必须用消息 id，不得用序号——存储里消息没有序号，只有全局唯一 id。分界 id 在历史里找不到时（事件流被手动改过、消息被删），该分界及更早的段作废：作废点之后全部按原文处理，`session_search` 对找不到 `upto` 的压缩段直接跳过（不误扫整条流）。

**旧格式兼容**：meta 没有 `compaction` 但有旧字段 `compactedSummary`/`compactedUpto` 的会话，读取时把旧摘要当作总摘要的起点（`top` = 旧摘要，`segments` 为空），保留部分仍按旧 `compactedUpto` 分界。`compactedSummary`/`compactedUpto` 不再被清除，但运行侧读压缩视图时 `compaction` 优先（run.ts 的 `prev` 先读 `compaction`，见 [storage](./storage.md)），两者并存无功能影响。不写迁移脚本；升级之前的会话没有 `compaction` 事件，`session_search` 返回"无可检索内容"——直到第一次压缩（只影响老会话）。

### 压缩审计（compaction 事件）

每次压缩成功后往会话事件流追加一条 `compaction` 事件（`SessionStore.appendCompaction` → `appendEvent`，经 core 的 `appendJsonlLine`，与消息写入同一套断尾修复机制），payload 即压缩审计字段：

```ts
export interface CompactionRecord {
  at: string            // ISO-8601 压缩发生时间
  trigger: "auto" | "in-run" | "manual"   // 收尾 / 运行中 / 手动
  emergency?: true      // 超限紧急急救的标记；仅自动压缩可能携带
  focus?: string        // 手动压缩时用户给的重点说明
  from: string | null   // 被压缩段的第一条消息 id；null = 从会话开头（或旧格式升级点）起
  upto: string          // 被压缩段覆盖到的最后一条消息 id
  messages: number      // 被压缩段内的消息条数
  segmentSummary: string  // 本次生成的段摘要
  top: string           // 归并后的新总摘要
}
```

压缩失败不记录（失败等于压缩没发生，无审计对象）。读取走 `readCompactions` / `GET /sessions/:id/compactions`（从事件流过滤 `compaction` 事件的只读投影视图），无事件返回 `[]`。

### 会话检索（session_search）

压缩段没有独立的检索索引（旧 `index.db` / `SegmentIndex` 已删除）——`session_search` 每次调用现读事件流、按相邻压缩段的 `upto` 取增量段区间做朴素文本匹配，详见下文"会话检索（session_search）"一节。

## 机制一：触发与分界

### 分界在哪里

会话里有七条消息 m1 到 m7（m7 最新）。某次压缩决定：m1 到 m3 卷进摘要，m4 到 m7 保留原文。之后这个会话的结构是：

```
┌──────────────────────────────────────┐
│ m1  m2  m3                           │ ← 压缩段：m1–m3 这段连续消息。
│                                      │    原文不再发给模型（仍存在硬盘上）
│         分界：compaction.upto = "m3"
├──────────────────────────────────────┤
│ m4  m5  m6  m7                       │ ← 保留部分：每轮原样发给模型
└──────────────────────────────────────┘

每轮实际发给模型的内容 = 脉络项（一条承载总摘要的 user 消息） + m4–m7 的原文
```

会话继续变长之后再压缩一次（比如 m4、m5 也被压掉），结构变成：

```
┌────────────────────────┐
│ 压缩段 1 = m1–m3       │ → 段摘要 1（不变）
│ 压缩段 2 = m4–m5       │ → 段摘要 2（新生成，之后也不变）
├────────────────────────┤
│ m6  m7                 │ ← 保留部分
└────────────────────────┘

总摘要 = 模型把"段摘要 1 + 段摘要 2"归并的结果（每次压缩后重新生成）
```

### 何时触发

发送消息永远不等待压缩——没有"发送前预压缩"这个环节，回车后立即开始运行。压缩发生在五个互不重叠的时机，前四个自动、最后一个手动：

| 触发点 | 时机与条件 | phase（事件与内部标记） | 审计 trigger | 阻塞性 |
|--------|-----------|------------------------|--------------|--------|
| 后台预压 | 迭代边界：占用估算进入 [预压线, 红线) 区间且没有正在执行的压缩、无暂存成果、无取消标记 | `in-run` | `in-run`（审计页显示"自动（运行中）"） | 不阻塞（后台进行） |
| 中途压缩 | 迭代边界：占用估算 ≥ 红线 | `in-run` | `in-run` | 挡下一次模型调用 |
| 收尾压缩 | `runAgent` 返回之后：run 以非 aborted/error 终态结束且占用估算 ≥ 黄线 | `post-run` | `auto` | 挡下一条出队消息 |
| 超限紧急急救 | 一次流式调用抛出上下文超限错误且零输出：不看阈值线，"已经爆了"就是事实 | `in-run` | `in-run` 加 `emergency: true` | 阻塞（救援） |
| 手动 /compact | 用户主动调用，跳过一切触发线 | `manual` | `manual` | 忙时排队（见"手动压缩"） |

占用估算来自 `estimateContextTokens(会话历史)`：锚定最后一条助手消息记录的真实 `usage.inputTokens`（上一次实际发出的请求大小），锚之后的新消息按字符粗算。锚定使已被压缩的旧内容天然不计入——它们根本不在上一次请求里——所以直接对全量历史读数即可，不需要先切出未压缩部分。没有锚点的窗口（新会话首条、压缩后的首请求）由显式的固定开销项补上：run 装配在系统提示词定稿后按字符粗算一次"系统提示词 + 工具定义"的估算值，占用读数在无锚点时加上这一项（有锚点时不加——锚点里的 `inputTokens` 已包含它，再加就重复计）。

各时机与正在执行的压缩的关系遵循一条不变量：**任何时刻同一会话至多一个压缩在跑**。后台预压（`compaction-check` 位置的内置钩子 `background-precompact`，见 [hooks](./hooks.md)）只在没有正在执行的压缩、没有暂存成果时开工；中途压缩（`mid-run-panic`）遇到正在执行的后台压缩时等它结束，再按暂存视图的分界重估活跃段——仍超红线才同步压，否则直接应用后台成果；收尾压缩（`post-run-compaction`，收尾路径里 await）遇到正在执行的后台压缩同样先等（循环已结束，暂存视图取走丢弃——元数据已携带同一成果）。超限急救（`overflow-rescue` 位置的 `overflow-emergency`）是唯一的例外——救援路径等不得，先掐掉正在执行的后台压缩再立即同步急救，被掐掉的成果丢弃（原文无损，下次重压；掐掉走 `abortInFlight` 不写取消标记——`cancel` 的标记会压制紧随其后的急救本身）。中途压缩与收尾压缩成功后的新压缩视图从下一次请求开始生效；超限急救成功后整次请求静默重发一次。

急救有独立的强制分界保底（`emergencyBoundary`，`session/compaction.ts`）：急救通常发生在压缩后的首请求或单轮工具输出暴涨时，`active` 里可能没有助手锚点、固定开销全漏计，`chooseBoundary` 据此可能找不到边界——此时不看预算，直接退守最小可行上下文：只保留最近一轮用户轮次（最后一条 user 消息及其之后的整轮），更早的全部压掉；整个 `active` 只有一轮时返回无可压缩。

五条线的分工（默认值）：省略线（`compactPackRatio`，0.70）在每次构造请求时免费削掉装不下的旧工具输出；预压线（`compactAheadRatio`，0.75）到线就派后台压缩，前台无感；黄线（`compactAtRatio`，0.80）配收尾压缩——一次压缩就把保留部分压到预算的三分之一（`compactTargetRatio` 默认 0.33），余量已够；红线（`compactPanicRatio`，0.90）配中途压缩，防运行内部工具输出累积把占用推向预算，也是后台压缩的触发上限（占用已过红线就直接同步压，不再绕后台）。压完留 33%，意味着之后要再积累约 1.27 倍预算的新对话才到预压线（压缩要花两次模型调用，不能太频繁）；运行内更细粒度的膨胀由机制三在每次构造请求时按省略线自动省略，红线是它之上的保险。五条线的缺省值、加载校验与"预算 × 比例 → 绝对 token 阈值"的解析集中在压缩水位线模块（`session/waterlines.ts` 的 `resolveWaterlines`）：配置加载时校验——触发四线（预压/黄/红/目标）越出 (0,1] 或次序不满足"目标 < 预压 < 黄 < 红"就整组回落默认并告警，省略线单独校验、独立回落；每次 run 解析出绝对阈值，触发钩子与压缩引擎读同一份。

自动压缩可以取消：WebUI 压缩指示行的"取消"按钮发 WS 帧 `compaction.cancel`，服务端中止正在执行的摘要调用（含后台预压），并写一个会话级取消标记——本次运行内后续的自动压缩（中途、收尾、后台预压，以及超限急救——它走自动压缩的共用装配入口 `Compactor.auto`，标记在时同样不开工）都被这个标记压制，下一次运行开始时标记清除、恢复正常压缩（服务端细节见 [run-manager](../server/run-manager.md) 的 `cancelCompaction`）。运行被用户中止时正在执行的后台压缩**不**随之中止：它的成果照常写入元数据，下次运行直接受益；daemon 退出时它被掐断，等于没发生。手动 /compact 不检查取消标记、与自动压缩互不干涉，WebUI 对手动阶段也不渲染取消按钮（`cancelCompaction` 不作用于手动压缩）。

### 分界怎么选

`chooseBoundary(active, { budget, targetRatio })` 三步（以预算 128,000、估算 90,000 为例，目标保留约 42,000）：

1. **从最新一条消息往回逐条累加估算值，加到 42,000 左右停下。** 圈出保留的部分：从停的位置到最新一条都按原文保留，更早的才去压缩。
2. **保留范围的起点对齐到最近的一条用户消息。** 从停的位置再往前扩几条，方向固定往多调——保留部分只会比目标多、不会少，压掉的两段都是完整轮次。
3. **要压缩的段 = 上一次的分界到保留范围起点之间。** 接上图例：第一次压缩分界在 m3，会话长到 m12 后再次触发，保留范围是 m8–m12，这次要压缩的就是 m4–m7（不是 m1–m7——m1–m3 已压缩过）：

```
m1  m2  m3 │ m4  m5  m6  m7 │ m8 … m12
已压缩过     │ 这次要压缩的段   │ 这次保留的
（段摘要已存）│（生成新段摘要）  │（原文继续发）
            ↑
       上一次的分界
```

本轮的用户消息就在最新端，天然落在保留范围内。三种情况本次不压缩、对话照常继续：整个历史的逐条估算加起来都到不了保留目标（上下文大在基准而非历史里，没有值得压的内容）；历史里找不到用户消息；保留范围起点就是第一条消息（压不出非空的段）。

**"约 33%"不是精确保证。** 估算本身有偏差、逐条累加的最后一条会让总量略过目标、对齐用户消息只往多的方向调——三个误差方向一致，实际结果略超 33%（例如 35%）而无妨：保留部分偏大只会让下次压缩来得稍早，不会把上下文装爆。压缩后每轮发送量 = 保留部分 + 脉络项（几百 token）+ 系统提示和工具定义（固定开销，本来就含在估算基准里），总量仍远低于触发线。一个已知的短期偏差：压缩发生后、下一条助手消息产生之前，估算基准还是压缩前那次请求的大小（偏大），这个窗口最多延续到下一次运行的首条请求；期间分界算法会发现保留部分已在目标以内而拒绝再压缩，新一轮请求产生新的助手消息后基准自动恢复准确。

## 机制二：分层摘要

### 摘要输入文本的构造（`renderSegment`）

一段历史转成文本，一条消息一行（`<role>: <内容>`）：

- text 和 note 块的文本以空格拼接。
- assistant 消息中的 tool_call 块追加为 `→ 工具名(参数 JSON，截 120 字)`。
- tool 消息的 tool_result 块渲染为 `⇐ 结果开头 300 字`，调用失败加 `[错误] ` 前缀。**失败的结果保留头尾两段**（错误原因几乎总在输出的末尾，额外保留尾部 200 字、中段以 `…[中略]…` 省略——摘要器看不到就总结不了）；成功的结果仍只截头部。
- **溢出存盘的定位行原样保留**：输出以 `[完整输出已存盘: <路径>]` 结尾时，该行先于截断切出、逐字进入渲染文本——指向全量副本的指针永远不会被截断切掉。
- 没有任何可渲染内容的消息显示为 `<tool use>`。
- 每行超过 2000 字符截断。

这样"模型读过什么、改过什么、得到了什么"以缩写形式进入摘要输入。记忆自动提取管线与压缩**共用这个构造函数**（提取质量同步受益）。

### 第一次调用：段摘要

输入是 `renderSegment(新段)`，system prompt 固定为：

> 你是对话摘要器。把给定的一段对话（可能包含工具调用与结果）压缩为不超过800字的中文摘要，使用以下固定五个二级标题的 markdown 结构：## 关键事实、## 用户偏好与约定、## 已做决定、## 未完成事项、## 文件与命令。"文件与命令"一栏只记路径或命令加一句话要点，不要复制文件内容。同一栏目内每条一行。摘要中的精确标识符——文件路径、命令、报错关键串、代码标识符、版本号、专有名词——必须逐字保留，不得意译或改写，后续检索全靠它们。直接输出摘要正文，不要任何前后缀。

"文件与命令"只记路径加一句要点：文件内容不用背下来，模型之后可以自己重新读。逐字保留精确标识符是压缩质量的提示词层守卫：摘要丢了 `ERR_MODULE_NOT_FOUND` 或 `packages/core/src/session/compactor.ts` 这样的精确串，后续的 `session_search` 关键词检索就再也命不中原事。一份段摘要的实际样子：

```markdown
## 关键事实
- 用户在开发 kclaw 的上下文压缩机制，方案是"预算 + 分段摘要 + 工具输出省略"三层
- 会话存储是 JSONL，消息只有全局唯一 id，没有序号

## 用户偏好与约定
- 回复用中文
- 不引入 tokenizer 依赖库

## 已做决定
- 触发条件从消息条数改成 token 估算
- 分界必须落在用户消息上

## 未完成事项
- docs/core 有四篇文档要更新

## 文件与命令
- packages/core/src/session/compactor.ts — 压缩引擎 Compactor.compact
- packages/core/src/agent/context.ts — 请求构造函数 toProviderMessages
```

### 第二次调用：归并总摘要

输入是"旧总摘要 + 新段摘要"两份文本（首次压缩没有旧总摘要时输入只有新段摘要，归并调用顺带把它规范成五栏格式），system prompt 固定为：

> 你是对话摘要归并器。输入是旧的总摘要和一个新的段摘要，两者都是同样五栏结构的 markdown。把它们归并为一份新的总摘要：保持同样的五个二级标题；同一栏目内合并去重；同一事项有先后版本时保留新版本，并注明被推翻的旧版本；总长不超过800字。归并时精确标识符（文件路径、命令、报错关键串、代码标识符、版本号、专有名词）必须逐字保留，不得改写。直接输出摘要正文，不要任何前后缀。

归并是链式的：每次只合并两份输入，旧总摘要本来就浓缩了之前全部段落，链式结果等价于所有段的归并，且每次调用的输入大小恒定，不随会话长度增长。冲突的处理示例：段摘要 1 记着"已做决定：分界按条数保留 25 条"，段摘要 2 记着"分界改为按 token 目标 33%"，归并后是"分界按 token 目标 33%（早期版本按条数，已被推翻）"。

800 字上限是有意的取舍：段落多了之后要点装不下是常态，装不下的细节只留在段摘要里（段摘要以 `compaction` 事件持久化在事件流里，`session_search` 可检索），总摘要只负责脉络；模型要具体内容用 `session_search` 查段原文（见下文）。

**溢出存盘指针结构化保留**：两次摘要调用之外，压缩引擎另把本次被压段里全部 `[完整输出已存盘: <路径>]` 定位行**结构性地**追加进段摘要与总摘要（对旧总摘要去重——归并继承的指针不重复记）。定位行不靠提示词自觉、由代码保证存活：压缩后全量副本仍可经 `fs_read` 读回；长内容本身永不内联进摘要——把体积搬进摘要只是换个每次请求都要付钱的地方。

两次调用都使用主对话模型、不带工具、用 `collectStreamText` 收集结果；自动路径传入取消信号（`collectStreamText` 支持中止，信号触发时抛出、已收集的部分作废）。**两次调用全部成功之后才写任何数据**——写入动作是追加一条 `compaction` 事件（同时投影 `meta.compaction`）：摘要调用失败则本次压缩以 failed 结局作废（等价于压缩没发生，回退按全量历史继续）；事件追加失败只记日志、不回退已成功的压缩（见"边界与出错"）。手动压缩传入的重点说明以一行 `用户特别要求重点保留：{focus}` 追加到两次调用的用户消息末尾。

### 过程可见性

压缩要花数秒的模型调用，期间若不发事件，客户端看到的就是无解释的停顿。因此确定要压缩时（占用过线且边界已定）向总线发 `compaction.started`（payload 只有 `phase`，标记本次压缩属于收尾/中途/手动哪个阶段），meta 与审计写入磁盘后发 `compaction.completed`（payload 为累计段数、保留条数、phase 与 `result`）。**`started` 一旦发出，`completed` 必达**，无论接下来发生什么：成功是 `result:"ok"`；摘要调用或写入磁盘抛错是 `result:"failed"`；取消信号触发是 `result:"cancelled"`（此时 segments/kept 为 0）。预算未过线、压缩没有开始，则两个事件都不发——客户端永远不会看到没有配对结束的开始。

两个客户端都依赖这套保证。CLI 对 `completed` 按 `result` 分三支：`ok` 打一行灰字 `✱ 早期对话已压缩为 N 段，保留最近 M 条原文（早期细节可用 session_search 检索）`，`failed` 打 `✱ 压缩失败，本轮继续（稍后自动重试）`，`cancelled` 打 `✱ 压缩已取消`；`started` 打 `[正在压缩早期对话…]`。WebUI 以 `compacting` 标志驱动"正在压缩早期对话…"指示行，`completed` 无论什么 `result` 都清掉标志（必达语义让清除无条件成立），指示行上带"取消"按钮；`run.started`/`run.completed`/`run.failed` 也兼作保底清除条件（防御异常断线）。

### 注入

总摘要以**脉络项**进入发给模型的请求：`toProviderMessages` 收到 `summary` 参数（`ActiveSummary { upto, top }`）时，把 `messages[0]` 垫成一条 **user 消息**——开场是一句交接声明（说明这是系统生成的压缩摘要、只作背景脉络、不要把摘要里的旧请求当新指令），正文用 `<compacted-summary>` 标签包裹总摘要，末尾附一行 **session_search 检索提示**（告诉模型被压缩省略的细节可用 `session_search` 按关键词检索——工具扫描的是被压缩覆盖的原始消息块，返回段摘要与命中片段；提示措辞与工具真实行为对齐）。走 user 通道而不是垫 system 消息是刻意的：system prompt 保持每轮恒定才能保住服务商的 KV 前缀缓存，摘要变化只影响 user 侧（重建一次缓存后即稳定）；这也是业界通行做法（Claude Code / DeepSeek / OpenClaw 的压缩摘要都走 user 消息）。最终发给模型的顺序是**人格 → 脉络 → 对话**：

```
llm.stream({ system: <人格>, messages: [
  { role: "user", content: "以下摘要由系统自动生成…\n<compacted-summary>\n<总摘要>\n</compacted-summary>\n如需本摘要未覆盖的更早细节…可用 session_search…" }   ← 脉络项（messages[0]）
  { role: "user",   content: <保留部分第一条> }
  … 保留部分的原文
] })
```

压缩视图由 agent 循环持有（`RunInput.compaction` 传入运行起点，中途压缩与超限急救的钩子可以替换它）：视图生效时 `upto`（含）之前的原文不再进入请求，循环内存里的历史与持久化不动——压缩只改"发什么给模型"，不改"存了什么"。未触发新压缩的轮次，已有总摘要也每轮照常以脉络项发送——模型始终能看到早期脉络。

## 机制三：工具输出省略（预算驱动）

位置在 `toProviderMessages`（`packages/core/src/agent/context.ts`）——所有发给模型供应商的请求都经它构造。两个可选参数共同决定哪些工具结果保留原文：`opts.toolResultKeep` 是**条数上限**（server 从配置 `sessions.toolResultKeep` 读值、默认 8，经 agent 循环的 `deps.toolResultKeep` 传入），`opts.tokenBudget` 是**省略预算**（run 装配传入省略线扣除固定开销后的余额：预算 × `compactPackRatio` − 系统提示词与工具定义的估算值）。不传时行为完全不变（全部保留）。

每次构造请求时分两步筛：

1. **条数上限**：从最新消息往前数，最近 8 个（`toolResultKeep`）工具结果进入候选，更早的直接换成占位符。这一步挡住的是极端长寿运行——比如 40 次工具调用的输出不可能都留着。
2. **预算装入**：先算基线——窗口内所有非工具结果内容（文本、thinking、note、工具调用参数、内联附件正文）的估算值，加上第 1 步已挤掉的结果按每条约 30 token 的占位成本；系统提示与工具定义的固定开销不在基线里，它们已从省略预算中预先扣除（见上）。然后从最新往回逐条把候选结果的估算值往基线上加：装得下的保留原文，遇到第一条装不下的，它连同比它更旧的全部换成占位符。

占位符是一行文字：

```
[此工具输出已省略：fs_read src/foo.ts，可重新调用获取]
```

占位符包含工具名与参数摘要（argsJson 前 60 字符）；该次调用失败的，占位符末尾加"（该次调用失败）"。前后对比：

```
不省略时，请求里是这样（每次都全量重发）：
  assistant: 调用 fs_read({"path":"src/foo.ts"})     ← 较早的一次
  tool:      src/foo.ts 的完整内容（约 4000 token）
  assistant: 调用 fs_read({"path":"src/bar.ts"})     ← 最近的一次
  tool:      src/bar.ts 的完整内容（约 3000 token）

省略后，请求里变成：
  assistant: 调用 fs_read({"path":"src/foo.ts"})
  tool:      [此工具输出已省略：fs_read src/foo.ts，可重新调用获取]
  assistant: 调用 fs_read({"path":"src/bar.ts"})
  tool:      src/bar.ts 的完整内容（约 3000 token）   ← 预算内、条数内，照常保留
```

替换只发生在发给供应商的请求数据里，会话 JSONL 一个字不动。它不会产生无效请求：工具调用和结果消息的配对关系没变，只是结果消息**里面的文本**换短了。运行中途的保护由此自动获得：agent 循环每次请求都要过这个函数，一次运行里连续几十次工具调用时，较早的输出自动被省略，上下文不会随调用次数线性膨胀；预算取省略线（70%）意味着"省略后的请求大小以省略线为界"——它在黄线之下，工具输出的省略永远走在压缩触发的前面，两者互不挤占。

## 机制四：后台预压缩

同步压缩的代价是等待：压缩要花两次模型调用、数秒时间，收尾压缩挡住下一条出队消息，中途压缩挡住下一次模型调用。后台预压缩把这次等待从关键路径上挪走——占用刚过预压线（75%）就开始在后台做摘要，等占用爬到黄线时大概率已经做完，同步路径一看占用已降回线以下就什么都不用做。整个机制由三块组成：

**触发**（`compaction-check` 位置的内置钩子 `background-precompact`，排在 `mid-run-panic` 之前）：每个迭代边界检查一次，条件全部满足才开工——占用估算落在 [预压线, 红线) 区间；该会话没有正在执行的压缩、无暂存成果、无取消标记；运行未被中止。占用过红线时不走后台——那是同步中途压缩的地盘（同步路径当场就能挡住下一次请求，后台救不了近火）。

**执行**（`Compactor.background`）：登记为正在执行（与同步路径同一张登记表，"同一会话至多一个压缩在跑"由此保证）后立即返回，摘要在后台进行。两个刻意的设计：

- **不挂 run 的中止信号**：用户中途取消运行时，正在执行的后台压缩照常跑完，成果照常写入元数据，下次运行直接受益；只有 daemon 退出会掐断它，等于没发生。
- **豁免黄线复核**（`background: true`）：普通自动压缩开工前会按黄线复核占用，预压区间本来就在黄线之下，这条复核会把后台压缩全部拦死，所以后台路径跳过它。

压缩本体与同步路径完全同一条代码路径（机制二的两次摘要调用、审计、事件一个不少）：`phase` 记 `in-run`、审计 trigger 记 `in-run`（审计页显示"自动（运行中）"），`compaction.started`/`completed` 照发——WebUI 的压缩指示行对后台压缩同样出现，取消按钮同样可用（`cancelCompaction` 掐的就是登记表里那个正在执行的任务）。

**完成与生效（双重交接）**：后台压缩完成时先把成果无条件写入——`compaction` 事件、`meta.compaction` 投影、总线事件全部落定；随后把新视图**暂存**在内存里（`takeParked` 可取）。应用发生在下一次迭代边界：`mid-run-panic` 在取消标记与中止信号都没命中后取暂存视图，有就直接采用为新压缩视图（暂存成立说明占用刚过预压线时压的，现在大概率已降回线以下，不再压第二次）——当前运行的下一次请求立刻变小；取消标记压着本次运行时不应用，暂存留在原地，由下一次运行取用。暂存视图只在内存：daemon 重启会丢掉暂存本身，但元数据已经写入磁盘，下次运行从 meta 读到同样的压缩视图，无损失。

与各同步路径的相处规则（详见"何时触发"一节的不变量）：

| 场景 | 行为 |
|------|------|
| 同步压缩**成功**时已有暂存视图 | 丢弃暂存：同步结果基于的元数据已含后台成果，再应用旧视图等于把压缩视图回滚。只在成功时作废——同步压缩没写成（占用/边界拦下、摘要失败）什么都没写，暂存成果仍是最新视图，保底照常可用 |
| 中途压缩遇到正在执行的后台压缩 | 等它落定，按暂存视图的分界重估活跃段（重估读数受旧锚点影响偏高，安全方向）：仍超红线才同步压（活跃段切不出边界就放弃硬压），否则直接应用暂存成果 |
| 收尾压缩遇到正在执行的后台压缩 | 等它落定（暂存视图取走丢弃——循环已结束，元数据已携带同一成果），再按黄线正常判断 |
| 超限急救遇到正在执行的后台压缩 | 等不得：先掐掉正在执行的压缩再立即急救，被掐的成果丢弃（原文无损，下次重压） |

## 会话检索（session_search）

- **检索函数**（`packages/core/src/tools/session-search.ts` 的 `searchSessionEvents`，纯函数）：每次调用都重新读一遍会话完整事件流（run 装配侧的 `buildSessionSearch` 经 `SessionStore.readEvents` 读入），只对压缩段做匹配——对每条 `compaction` 事件，取它覆盖的段区间（`(上一段 upto, 本段 upto]` 内的 `message` 事件，按相邻 `upto` 划分、每条消息只归属一段），把 query 对该段消息块做**朴素包含匹配**（`JSON.stringify(blocks)` 的子串判断，不切词、不建索引），命中归到该压缩事件的段摘要；`compaction` 事件的 `upto` 在流里找不到则跳过该段（不误扫整条流）；没有 `compaction` 事件或没有命中返回空。
- **工具**（`packages/core/src/tools/session.ts` 的 `createSessionTools`）：

| 项 | 值 |
|----|----|
| 参数 | `{ query: string（必填）, limit?: number }`，limit 默认 5、上限 20 |
| 权限分类 | 与 `memory_search` 相同：safe + parallel（免确认、可并发） |
| 检索范围 | 只检索当前会话的压缩段（扫该会话事件流） |
| 输出 | 每个命中一行 `- <段摘要>` 加缩进的文本片段（该段消息块序列化文本的前 200 字符） |
| 无内容 | 会话没有压缩段、或没有命中时返回 `(无可检索内容)` |

工具始终注册（工具列表不随会话状态变化，未注入检索函数时同样返回 `(无可检索内容)`）；检索函数由 run 装配（core `executeRun`）每个 run 懒构造（`buildSessionSearch`），每次调用都重新读一遍该会话事件流，没有需要维护或重建的持久索引。

## 手动压缩（/compact）

不看触发线，对当前历史执行一次压缩——与自动压缩走同一条代码路径（`RunManager.compactSession` 内部调 core `Compactor.compact`，`manual: true`）。三个入口：

- **HTTP**：`POST /sessions/:id/compact`，请求体可选 `{ "focus": "重点保留什么的一段说明" }`（见 [http-api](../server/http-api.md)）。
- **CLI**：`/compact [重点说明]`，转发到上述接口（`packages/cli/src/slash.ts`）。
- **web**：`/compact [重点说明]` 命令，调同一接口（`packages/web/src/chat/commands.ts`）。

会话空闲时立即执行，完成后返回一句话：`压缩了 N 段，剩 X 条原文消息`；历史太短没有可压缩内容时返回 `无可压缩内容`，不产生任何状态变化。三条约束：

- **手动压缩不产生新消息**：总摘要以脉络项进入下一次请求（和自动压缩同一路径），命令的即时反馈只有确认文本；可追溯性由压缩审计承担（见下节）。
- **会话正在运行时排队等待，不再拒绝**：run 活动期间收到 /compact，返回 `{ queued: true, message: "已排队：当前运行结束后自动压缩" }`（HTTP 200），请求排队记在内存里；运行结束的收尾链在自动收尾压缩**之前**先冲刷排队的手动压缩（内置钩子 `manual-compact-flush`），用户拿到的就是自己点的那次压缩，而不是先被自动压缩捷足先登。排队期间再次 /compact 以后来的 focus 覆盖先前的（用户要的永远是最后一次指示）；排队只在内存，daemon 重启即丢。排队的手动压缩跳过忙碌/排队拒绝检查——它本来就在"运行结束后"这个时点执行，此刻队列里有消息是常态而非异常。
- **已有排队消息时仍拒绝**：会话不在运行、但队列里已有等待消息时返回 409——排队消息会连开多个 run，压缩窗口无法预期，保持显式拒绝（"还有 N 条排队消息，先处理或取消"）。

## 压缩审计

`compaction` 事件是自动与手动压缩共同的记录载体（手动压缩刻意不产生消息，纯靠消息流看不到它的痕迹），作为 append-only 事件流里的一条追加在会话目录 `events.jsonl` 中；`GET /sessions/:id/compactions` 是它的只读投影视图（从事件流过滤 `compaction` 事件）。审计页（`packages/web/src/audit/AuditView.tsx`）改拉 `GET /sessions/:id/events` 单源，按事件流序把 `compaction` 事件渲染成一行"压缩"行：触发方式（`自动（收尾）` / `自动（运行中）` / `手动`，带 `emergency` 标记的追加"·超限急救"，手动显示 focus）、被压范围（`from`–`upto`，首条为 null 显示"会话开头"）、消息条数；点击展开该次的段摘要与总摘要全文。无记录时不显示。消息历史本身仍然没有专门的审计接口（见 [http-api](../server/http-api.md)）。

## 配置

`config.yaml` 的 `sessions` 段（`packages/core/src/storage/config.ts`；缺省值在读取处补齐）：

| 字段 | 默认 | 含义 |
|------|------|------|
| `contextTokens` | `128000` | 上下文 token 预算（与模型条目的 `contextWindow` 取较小者生效） |
| `compactPackRatio` | `0.70` | 省略线：工具输出省略的预算比例（机制三） |
| `compactAheadRatio` | `0.75` | 预压线：后台预压缩的触发下限（上限是红线，机制四） |
| `compactAtRatio` | `0.80` | 黄线：收尾压缩触发线 |
| `compactPanicRatio` | `0.90` | 红线：中途压缩触发线 |
| `compactTargetRatio` | `0.33` | 压缩后保留部分的目标大小（占预算比例） |
| `toolResultKeep` | `8` | 发送时保留工具结果原文的**最多条数**（预算驱动省略的条数上限） |

模型条目侧的两个可选字段（`providers.entries.<key>`）：`contextWindow` 是该模型的上下文窗口，作为预算上限参与 `resolveContextTokens` 的 min 解析；`maxOutput` 是单次回复的输出上限，run 装配经 agent 循环随每个请求下发为 `max_tokens`（缺省不下发，沿用供应商默认）。

废弃：`compactThreshold`（旧版 40 条触发）与 `compactKeep`（旧版保留 25 条）。配置文件里存在时不报错，但不再起作用。

## 边界与出错

原则：检索与审计相关的一切失败只记日志；摘要生成失败则放弃本次压缩，运行照常继续。

| 失败点 | 行为 |
|--------|------|
| 收尾压缩的摘要调用失败 | 记日志 + 发 `completed {result:"failed"}`，不写审计记录；下一次收尾或中途过线重新触发 |
| 中途压缩的摘要调用失败 | 同上；运行不补救继续，靠工具输出省略保底 |
| 后台预压的摘要调用失败 | 记 `kclaw compaction (background) failed:` 日志 + 发 `completed {result:"failed"}`；失败等于没发生，不产生暂存，下个迭代边界可重试 |
| 中途压缩被用户取消 | 发 `completed {result:"cancelled"}`，不写压缩事件/投影；本次运行内不再自动触发（取消标记，后台预压同样受制），下次运行恢复正常 |
| 中途压缩被中止信号打断 | 同取消；运行本身走中止路径 |
| 运行被用户中止时正在执行的后台预压 | 不随之中止：照常跑完并写入元数据（下次运行受益）；daemon 退出时被掐断，等于没发生 |
| 压缩审计（compaction 事件）追加失败 | 压缩照常生效，只记 `kclaw compaction audit … append failed:` 日志；不得因审计失败回退已成功的压缩（投影缺口可经 `rebuildMeta` 从事件流整流重建） |
| 分界消息 id 在历史里找不到 | 压缩状态作废，作废点之后全部按原文处理；`session_search` 对找不到 `upto` 的压缩段直接跳过 |
| 请求真超限（前面所有手段失守） | 识别上下文超限错误 → 掐掉正在执行的后台压缩 → 紧急压缩 → 整次请求静默重发一次；重发仍超限才把错误报给用户 |
| 收尾压缩期间用户发消息 | 会话保持忙碌，新消息走既有排队路径，压缩完成后自动开跑 |
| 会话运行中调 /compact | 排队：返回"已排队：当前运行结束后自动压缩"，运行结束收尾链先冲刷它再做自动收尾压缩 |
| 会话有排队消息时调 /compact | 拒绝，返回"还有 N 条排队消息，先处理或取消" |
