# compaction — 上下文压缩

## 职责

会话聊得越长，每次发给模型的上下文就越大，大到超出模型窗口后请求会直接失败。压缩机制把较早的对话转换成摘要、之后不再按原文发送，让每轮发送量回到预算以内；被压掉的细节仍然留在硬盘上，并可通过全文检索找回来。整套机制分三层，互相独立：

1. **触发与分界**（`packages/core/src/session/compaction.ts` 的 `estimateContextTokens` / `chooseBoundary`）：按 token 估算判断何时压缩、压到哪里。
2. **分层摘要**（同一模块的 `renderSegment` 加 `packages/server/src/run.ts` 的 `#compactV2` 编排）：两次不带工具的模型调用，先给新压掉的段生成"段摘要"，再归并进"总摘要"。
3. **工具输出省略**（`packages/core/src/agent/context.ts` 的 `toProviderMessages`）：发送前把较旧的工具结果换成一行说明文字，防止一次运行内的多次工具调用把上下文撑爆。

外围还有三件配套物：会话级检索索引（`packages/core/src/session/segment-index.ts`）与 `session_search` 工具（`packages/core/src/tools/session.ts`）负责"找得回来"；手动压缩（`RunManager.compactSession` + HTTP/CLI/web 三个入口）负责"人能主动压"；压缩审计（会话目录下的 `compactions.jsonl`）负责"压过之后查得到"。调模型与写盘的编排全部在 server 侧，core 只提供可独立测试的纯函数。

## 设计决策

- **按 token 触发，不按消息条数**：一条消息可能是 10 个字也可能是一次返回 100KB 的工具输出，条数说明不了上下文大小。触发判断用估算：基准取最近一次真实请求的大小（最后一条助手消息记录的 `usage.inputTokens`，模型供应商返回的真实数字，天然含系统提示与工具定义的固定开销），基准之后的新消息按字符粗算（`estimateTokens`：CJK 字符每个记 0.75 个 token，其余字符四个记 1 个，结果向上取整）。估算整体偏大而非偏小——偏大只会让压缩提前发生，方向安全。
- **细节只损失一次**：旧机制每次压缩都把旧摘要重新压一遍，细节一轮轮丢失。v2 把摘要拆成两层——**段摘要**针对一段对话生成之后永不修改，**总摘要**只做"旧总摘要 + 新段摘要"的归并。细节只在新段摘要素成时损失一次，总摘要随时可以从全部段摘要重跑归并重新生成（段摘要是不变的底稿，不依赖对话原文）。
- **保留部分对齐用户消息**：分界起点固定落在一条用户消息上，保证压掉的段和保留的部分都是从"用户提问"开始的完整轮次，工具调用和它的结果永远在同一侧——OpenAI 兼容接口要求两者配对出现，拆开会直接报错。
- **任何一层失败都退回全量运行**：摘要调用或 meta 写入抛错时只记一行 `kclaw compaction failed:` 日志，本次运行带完整历史照常执行，下一轮重新触发。最坏情况等于"没有压缩"，不会比现状差。
- **索引与审计是外围，不是前提**：检索索引删了可以随时从会话原文重建；审计追加失败只记日志，不让已成功的压缩回退。
- **循环窗口退居保险**：agent 循环"最多取最近 N 条消息"的硬上限从 40 放宽到 200（`packages/core/src/agent/loop.ts`），角色从主要控制手段退化为防止估算彻底失准的极端保险。

## 术语

| 术语 | 含义 |
|------|------|
| 压缩 | 把较早的对话消息转换成摘要、之后不再按原文发送的过程。原文始终保留在硬盘上。 |
| 压缩段（段） | 一次压缩中被转换成摘要的那段连续消息。 |
| 段摘要 | 针对一个压缩段生成的摘要，固定五个栏目（见下文），生成之后永不修改。 |
| 总摘要 | 所有段摘要归并成的一份完整脉络，每轮发给模型的就是它。 |
| 分界 | 压缩内容和保留原文部分的边界，用一条消息的 id 表示。 |
| 保留部分 | 分界之后、继续按原文发送的近期历史。 |
| 预算 | 一个会话允许的上下文 token 上限（配置 `sessions.contextTokens`，默认 128000）。 |
| 触发线 | 预算的 66%；估算发送量达到它就执行压缩。 |
| 工具输出省略 | 发送请求前把较旧的工具结果文本替换成一行说明文字；只影响发出的请求，不影响存储。 |

## 数据模型

压缩状态分布在会话目录的三个文件里（目录结构见 [storage](./storage.md)）：

### meta.json 的 `compaction` 字段

`SessionMeta`（`packages/core/src/session/store.ts`）上的可选字段，类型定义在 `packages/core/src/session/compaction.ts`：

```ts
export interface CompactionSegment { upto: string; summary: string }
export interface CompactionState { segments: CompactionSegment[]; top: string; upto: string }
```

| 字段 | 含义 |
|------|------|
| `segments[].upto` | 这个压缩段覆盖到的最后一条消息 id（含它） |
| `segments[].summary` | 这个段的段摘要 |
| `top` | 总摘要 |
| `upto` | 总分界：这条消息之前（含它）都已压缩，之后的是保留部分（等于末段的 `upto`） |

段的消息范围由相邻两个 `upto` 界定：第一段从会话开头（或旧格式升级点）到 `segments[0].upto`，其后每段从前一段的 `upto` 之后到本段 `upto`（`segmentRanges` 负责映射）。分界必须用消息 id，不得用序号——存储里消息没有序号，只有全局唯一 id。分界 id 在历史里找不到时（JSONL 被手动改过、消息被删），该分界及更早的段作废：作废点之后全部按原文处理，索引重建跳过作废段。

**旧格式兼容**：meta 没有 `compaction` 但有旧字段 `compactedSummary`/`compactedUpto` 的会话，读取时把旧摘要当作总摘要的起点（`top` = 旧摘要，`segments` 为空），保留部分仍按旧 `compactedUpto` 分界；下一次压缩发生时结果写入新格式，同时删除旧字段（`updateMeta` 传 `undefined` patch）。不写迁移脚本；升级之前的内容没有分段记录，进不了检索索引——只影响老会话。

### compactions.jsonl（压缩审计）

每次压缩成功后追加一行 JSON（`SessionStore.appendCompaction`，经 core 的 `appendJsonlLine`，与消息写入同一套断尾修复机制）：

```ts
export interface CompactionRecord {
  at: string            // ISO-8601 压缩发生时间
  trigger: "auto" | "manual"
  focus?: string        // 手动压缩时用户给的重点说明
  from: string | null   // 被压缩段的第一条消息 id；null = 从会话开头（或旧格式升级点）起
  upto: string          // 被压缩段覆盖到的最后一条消息 id
  messages: number      // 被压缩段内的消息条数
  segmentSummary: string  // 本次生成的段摘要
  top: string           // 归并后的新总摘要
}
```

压缩失败不记录（失败等于压缩没发生，无审计对象）。读取走 `readCompactions` / `GET /sessions/:id/compactions`，文件缺失返回 `[]`。

### index.db（会话检索索引）

`~/.kclaw/sessions/<id>/index.db`，SQLite FTS5 全文索引（FTS5 是 SQLite 的全文检索扩展），两张表：`segments`（upto 主键，存段摘要与段全文）与 `segments_fts`（分词后的 token 串，靠 rowid 对应）。和会话同生共死，删除会话时随目录一起删；它只是可再生的缓存，任何时候删除都不丢数据。

## 机制一：触发与分界

### 分界在哪里

会话里有七条消息 m1 到 m7（m7 最新）。某次压缩决定：m1 到 m3 卷进摘要，m4 到 m7 保留原文。之后这个会话的结构是：

```
┌──────────────────────────────────────┐
│ m1  m2  m3                           │ ← 压缩段：m1–m3 这段连续消息。
│                                      │    原文不再发给模型（仍存在硬盘上）
│         分界：compaction.upto = "m3"
├──────────────────────────────────────┤
│ m4  m5  m6  m7                       │ ← 保留部分：每轮原样发给模型
└──────────────────────────────────────┘

每轮实际发给模型的内容 = 总摘要（一段文字） + m4–m7 的原文
```

会话继续变长之后再压缩一次（比如 m4、m5 也被压掉），结构变成：

```
┌────────────────────────┐
│ 压缩段 1 = m1–m3       │ → 段摘要 1（不变）
│ 压缩段 2 = m4–m5       │ → 段摘要 2（新生成，之后也不变）
├────────────────────────┤
│ m6  m7                 │ ← 保留部分
└────────────────────────┘

总摘要 = 模型把"段摘要 1 + 段摘要 2"归并的结果（每次压缩后重新生成）
```

### 何时触发

每次运行开始前，对"未被压缩的历史 + 本轮用户消息文本"做估算（`estimateContextTokens`）。估算达到预算 × 0.66（`sessions.compactAtRatio`，下同）就压缩。压缩的目标是**保留部分约为预算的三分之一**（`compactTargetRatio` 默认 0.33）：压完留 33%，意味着之后要再积累一倍的新对话才会再次触发（压缩要花两次模型调用，不能太频繁）；默认预算 128000 的三分之一（约 42,000 token）的原文量也足够模型记住当前任务的来龙去脉。

不设第二级"紧急压缩"触发线：一次压缩就从 66% 降到 33%，余量已够；一次运行进行中上下文膨胀的主要来源是大工具输出，那由机制三在每次请求时自动处理。

### 分界怎么选

`chooseBoundary(active, { budget, targetRatio })` 三步（以预算 128,000、估算 90,000 为例，目标保留约 42,000）：

1. **从最新一条消息往回逐条累加估算值，加到 42,000 左右停下。** 圈出保留的部分：从停的位置到最新一条都按原文保留，更早的才去压缩。
2. **保留范围的起点对齐到最近的一条用户消息。** 从停的位置再往前扩几条，方向固定往多调——保留部分只会比目标多、不会少，压掉的两段都是完整轮次。
3. **要压缩的段 = 上一次的分界到保留范围起点之间。** 接上图例：第一次压缩分界在 m3，会话长到 m12 后再次触发，保留范围是 m8–m12，这次要压缩的就是 m4–m7（不是 m1–m7——m1–m3 已压缩过）：

```
m1  m2  m3 │ m4  m5  m6  m7 │ m8 … m12
已压缩过     │ 这次要压缩的段   │ 这次保留的
（段摘要已存）│（生成新段摘要）  │（原文继续发）
            ↑
       上一次的分界
```

本轮正在回答的用户消息天然在保留范围内——它由循环拼在保留部分之后。三种情况本次不压缩、退回全量运行照常执行：整个历史的逐条估算加起来都到不了保留目标（上下文大在基准而非历史里，没有值得压的内容）；历史里找不到用户消息；保留范围起点就是第一条消息（压不出非空的段）。

**"约 33%"不是精确保证。** 估算本身有偏差、逐条累加的最后一条会让总量略过目标、对齐用户消息只往多的方向调——三个误差方向一致，实际结果略超 33%（例如 35%）而无妨：保留部分偏大只会让下次压缩来得稍早，不会把上下文装爆。压缩后每轮发送量 = 保留部分 + 总摘要（几百 token）+ 系统提示和工具定义（固定开销，本来就含在估算基准里），总量仍远低于触发线。一个已知的短期偏差：压缩发生后、下一条助手消息产生之前，估算基准还是压缩前那次请求的大小（偏大），最多存在一次运行；期间分界算法会发现保留部分已在目标以内而拒绝再压缩，新一轮运行产生新的助手消息后基准自动恢复准确。

## 机制二：分层摘要

### 摘要输入文本的构造（`renderSegment`）

一段历史转成文本，一条消息一行（`<role>: <内容>`）：

- text 和 note 块的文本以空格拼接；**kind 为 `compact` 的 note 必须排除**——它的内容就是旧总摘要的注入痕迹，已存在 meta 里，再进输入就重复了。
- assistant 消息中的 tool_call 块追加为 `→ 工具名(参数 JSON，截 120 字)`。
- tool 消息的 tool_result 块渲染为 `⇐ 结果开头 300 字`，调用失败加 `[错误] ` 前缀。
- 没有任何可渲染内容的消息显示为 `<tool use>`。
- 每行超过 2000 字符截断。

这样"模型读过什么、改过什么、得到了什么"以缩写形式进入摘要输入。记忆自动提取管线与压缩**共用这个构造函数**（提取质量同步受益），分词器同理抽在 `packages/core/src/text/fts.ts` 供记忆索引与本模块的检索索引共用。

### 第一次调用：段摘要

输入是 `renderSegment(新段)`，system prompt 固定为：

> 你是对话摘要器。把给定的一段对话（可能包含工具调用与结果）压缩为不超过800字的中文摘要，使用以下固定五个二级标题的 markdown 结构：## 关键事实、## 用户偏好与约定、## 已做决定、## 未完成事项、## 文件与命令。"文件与命令"一栏只记路径或命令加一句话要点，不要复制文件内容。同一栏目内每条一行。直接输出摘要正文，不要任何前后缀。

"文件与命令"只记路径加一句要点：文件内容不用背下来，模型之后可以自己重新读。一份段摘要的实际样子：

```markdown
## 关键事实
- 用户在开发 kclaw 的上下文压缩机制，方案是"预算 + 分段摘要 + 工具输出省略"三层
- 会话存储是 JSONL，消息只有全局唯一 id，没有序号

## 用户偏好与约定
- 回复用中文
- 不引入 tokenizer 依赖库

## 已做决定
- 触发条件从消息条数改成 token 估算
- 分界必须落在用户消息上

## 未完成事项
- /compact 的 web 按钮还没做
- docs/core 有四篇文档要更新

## 文件与命令
- packages/server/src/run.ts — 现有压缩实现 #compact
- packages/core/src/agent/context.ts — 请求构造函数 toProviderMessages
```

### 第二次调用：归并总摘要

输入是"旧总摘要 + 新段摘要"两份文本（首次压缩没有旧总摘要时输入只有新段摘要，归并调用顺带把它规范成五栏格式），system prompt 固定为：

> 你是对话摘要归并器。输入是旧的总摘要和一个新的段摘要，两者都是同样五栏结构的 markdown。把它们归并为一份新的总摘要：保持同样的五个二级标题；同一栏目内合并去重；同一事项有先后版本时保留新版本，并注明被推翻的旧版本；总长不超过800字。直接输出摘要正文，不要任何前后缀。

归并是链式的：每次只合并两份输入，旧总摘要本来就浓缩了之前全部段落，链式结果等价于所有段的归并，且每次调用的输入大小恒定，不随会话长度增长。冲突的处理示例：段摘要 1 记着"已做决定：分界按条数保留 25 条"，段摘要 2 记着"分界改为按 token 目标 33%"，归并后是"分界按 token 目标 33%（早期版本按条数，已被推翻）"。

800 字上限是有意的取舍：段落多了之后要点装不下是常态，装不下的细节只留在段摘要里（meta 和检索索引都存着），总摘要只负责脉络；模型要具体内容用 `session_search` 查段全文（见下文）。

两次调用都使用主对话模型、不带工具、用 `collectStreamText` 收集结果。**两次调用全部成功之后才写任何数据**——meta 写入是摘要结果的唯一落盘动作，失败等于压缩没发生。手动压缩传入的重点说明以一行 `用户特别要求重点保留：{focus}` 追加到两次调用的用户消息末尾。

### 过程可见性

预压缩发生在 `run.started` 之前，摘要调用的数秒里若不发事件，客户端就是发送后的静默空窗。因此确定要压缩时（预算过线且边界已定）向总线发 `compaction.started`，meta 与审计落盘后发 `compaction.completed`（payload 为累计段数与保留条数）；预算未过线不压缩则两个事件都不发。压缩失败（摘要调用抛错）只发过 `started`、永远没有 `completed`——客户端把 `run.started`/`run.completed`/`run.failed` 也当作压缩状态的清除条件兜底。两个客户端都以 `completed` 为"每次压缩一条"的告知：CLI 打一行灰字 `✱ 早期对话已压缩为 N 段…`（started 只打 `[正在压缩早期对话…]`；带 meta 的 compact note 静默，无 meta 的旧格式仍打全文）；WebUI 压缩进行中显示"正在压缩早期对话…"指示行，折叠上下文条挂在消息上方，逐轮重挂的 note 靠段数去重。

### 注入

总摘要附在本轮用户消息上（沿用 note 注入路径和 `note.emitted` 事件，note 顺序 job → compact → memory），note 的 kind 为 `"compact"`，文本模板固定为：

> 早期对话已压缩为 {N} 段（保留最近 {X} 条原文；可用 session_search 检索早期细节）。摘要：
> {top}

未触发新压缩的轮次，已有总摘要也每轮照常附带——模型始终能看到早期脉络。

note 块还带一个**仅供 UI 使用**的可选字段 `compact: { segments, kept }`（`kept` 是保留尾部的条数，含本轮用户消息）。发给模型的请求只读 note 的 `text`（`[system note] ${text}`），这个字段模型永远看不到；WebUI 靠它把每轮重复挂载的 note 去重成"每次压缩一条折叠块"，展示约定见 [webui](../web/webui.md)。

## 机制三：工具输出省略

改动位置是 `toProviderMessages`（`packages/core/src/agent/context.ts`）——所有发给模型供应商的请求都经它构造。新增可选参数 `opts.toolResultKeep` 指定保留数量，不传时行为完全不变；server 从配置 `sessions.toolResultKeep`（默认 8）读值经 agent 循环的 `deps.toolResultKeep` 传入。

构造请求时从最新消息往前数，最近 8 个（`toolResultKeep`）工具结果原样保留，更早的把输出文本替换成一行：

```
[此工具输出已省略：fs_read src/foo.ts，可重新调用获取]
```

占位符包含工具名与参数摘要（argsJson 前 60 字符）；该次调用失败的，占位符末尾加"（该次调用失败）"。前后对比：

```
不省略时，请求里是这样（每次都全量重发）：
  assistant: 调用 fs_read({"path":"src/foo.ts"})     ← 较早的一次
  tool:      src/foo.ts 的完整内容（约 4000 token）
  assistant: 调用 fs_read({"path":"src/bar.ts"})     ← 最近的一次
  tool:      src/bar.ts 的完整内容（约 3000 token）

省略后，请求里变成：
  assistant: 调用 fs_read({"path":"src/foo.ts"})
  tool:      [此工具输出已省略：fs_read src/foo.ts，可重新调用获取]
  assistant: 调用 fs_read({"path":"src/bar.ts"})
  tool:      src/bar.ts 的完整内容（约 3000 token）   ← 最近 8 个之内，照常保留
```

替换只发生在发给供应商的请求数据里，会话 JSONL 一个字不动。它不会产生无效请求：工具调用和结果消息的配对关系没变，只是结果消息**里面的文本**换短了。运行中途的保护由此自动获得：agent 循环每次请求都要过这个函数，一次运行里连续几十次工具调用时，较早的输出自动被省略，上下文不会随调用次数线性膨胀。

## 会话检索（session_search）

- **索引**：每次压缩成功后，把新段的输入文本（给摘要模型看的那份 `renderSegment` 产物）和段摘要写进 `index.db`（`SegmentIndex.addSegment`，按 upto upsert）。检索时发现索引文件不存在而 meta 里有压缩段记录，就从会话 JSONL 按各段分界重新构造文本、重建索引（`SegmentIndex.ensure`；索引文件损坏同样删掉重建）。
- **中文分词**：与记忆系统共用 `packages/core/src/text/fts.ts` 的 `tokenize`——ASCII 字母数字串按整词（转小写），CJK 连续串拆成相邻两字组合（bigram），解决 FTS5 默认分词查不到中文的问题。
- **工具**（`packages/core/src/tools/session.ts`）：

| 项 | 值 |
|----|----|
| 参数 | `{ query: string（必填）, limit?: number }`，limit 默认 5、上限 20 |
| 权限分类 | 与 `memory_search` 相同：safe + parallel（免确认、可并发） |
| 检索范围 | 只检索当前会话的索引 |
| 输出 | 每个命中一行 `- <段摘要>` 加缩进的匹配位置文本片段（命中 token 前后各约 150 字符） |
| 无内容 | 会话没有压缩段时返回 `(无可检索内容)` |

工具始终注册（工具列表不随会话状态变化）；检索函数由 server 每个 run 懒构造（`#buildSessionSearch`，首次调用才打开/重建索引）。

## 手动压缩（/compact）

不看触发线，立即对当前历史执行一次压缩——与自动压缩走同一条代码路径（`RunManager.compactSession` 内部调 `#compactV2`，`manual: true`）。三个入口：

- **HTTP**：`POST /sessions/:id/compact`，请求体可选 `{ "focus": "重点保留什么的一段说明" }`（见 [http-api](../server/http-api.md)）。
- **CLI**：`/compact [重点说明]`，转发到上述接口（`packages/cli/src/slash.ts`）。
- **web**：会话输入区上方的"压缩"按钮，调同一接口（`packages/web/src/chat/ChatPanel.tsx`）。

完成后返回一句话：`压缩了 N 段，剩 X 条原文消息`；历史太短没有可压缩内容时返回 `无可压缩内容`，不产生任何状态变化。两条约束：

- **手动压缩不产生新消息**：总摘要仍挂在下一条用户消息上注入（和自动压缩同一路径），命令的即时反馈只有确认文本；可追溯性由压缩审计承担（见下节）。
- **会话正在运行时拒绝**：返回"会话正在运行"（HTTP 409）——压缩要读全量历史、写会话元数据，和运行中的写入并发会互相破坏。

---

## 压缩审计

`compactions.jsonl` 是自动与手动压缩共同的记录载体（手动压缩刻意不产生消息，纯靠消息流看不到它的痕迹）。审计页（`packages/web/src/audit/AuditView.tsx`）选中会话后额外拉取 `GET /sessions/:id/compactions`，在消息轨迹上方渲染"压缩记录"区块：每条记录一行——时间、触发方式（自动 / 手动，手动显示 focus）、被压范围（`from`–`upto`，首条为 null 显示"会话开头"）、消息条数；点击展开该次的段摘要与总摘要全文。无记录时不显示该区块。消息轨迹本身仍然没有专门的审计接口（见 [http-api](../server/http-api.md)）。

---

## 配置

`config.yaml` 的 `sessions` 段（`packages/core/src/storage/config.ts`；缺省值在读处兜底）：

| 字段 | 默认 | 含义 |
|------|------|------|
| `contextTokens` | `128000` | 上下文 token 预算 |
| `compactAtRatio` | `0.66` | 估算发送量达到"预算 × 此比例"即触发压缩 |
| `compactTargetRatio` | `0.33` | 压缩后保留部分的目标大小（占预算比例） |
| `toolResultKeep` | `8` | 发送时保留最近几个工具结果的原文 |

废弃：`compactThreshold`（旧版 40 条触发）与 `compactKeep`（旧版保留 25 条）。配置文件里存在时不报错，但不再起作用。

## 边界与出错

原则：检索和索引相关的一切失败只记日志；摘要生成和 meta 写入失败则放弃本次压缩，回退全量运行。

| 失败点 | 行为 |
|--------|------|
| 摘要的模型调用失败 | 记 `kclaw compaction failed:` 日志，本次全量运行，下轮重新触发；不写审计记录 |
| meta 写入失败 | 同上；meta 写入是摘要结果的唯一落盘动作，失败等于压缩没发生 |
| 段索引写入失败 | 压缩照常生效，只记 `kclaw segment index … write failed:` 日志；检索时靠重建兜底 |
| 审计记录追加失败 | 压缩照常生效，只记 `kclaw compaction audit … append failed:` 日志；不得因审计失败回退已成功的压缩 |
| 分界消息 id 在历史里找不到 | 压缩状态作废，作废点之后全部按原文处理；索引重建跳过作废段 |
| 估算失准、供应商报上下文超限 | 错误原样返回给用户（现状行为）；手动 /compact 是直接出路 |
| 会话运行中调 /compact | 拒绝，返回"会话正在运行" |
| 索引文件损坏 | 下次检索时删除重建（`ensure`），段数据以 meta 与会话原文为准 |
